## Data Architecture — Read This First

Project data is **not hardcoded.** It lives in a GitHub README and the site fetches it live at runtime, so updating that one file updates the deployed site with no frontend redeploy needed.

**How it works:**
1. On load, fetch the raw README from:
   `https://raw.githubusercontent.com/ashrma0502/My-Projects/main/README.md`
2. The README contains two hidden HTML comment blocks — invisible on GitHub's rendered view, present in the raw text:
   - `<!-- PROJECTS_JSON [...] PROJECTS_JSON_END -->`
   - `<!-- CERTIFICATES_JSON [...] CERTIFICATES_JSON_END -->`
3. Extract each with a regex (`/<!-- PROJECTS_JSON([\s\S]*?)PROJECTS_JSON_END -->/`), `JSON.parse()` the captured group, and use the result as the data source for the Projects and Certificates sections.

**Project object shape** (fields aren't all guaranteed present — code defensively):
```json
{
  "name": "Weather Dashboard",
  "description": "One-sentence summary.",
  "repo": "https://github.com/ashrma0502/Weather-App",
  "links": { "live": "https://weather-focus.vercel.app" },
  "techStack": ["React 19", "Vite", "Tailwind CSS"],
  "type": "college"
}
```
* `links` may be **absent** (not deployed — show a "Not deployed yet" badge instead of buttons), contain a single `live` key, or contain both `frontend` and `backend` keys (render as two separate buttons, not one).
* `type` is one of `"personal"`, `"college"`, `"hackathon"` — use it to power section grouping and filter tabs.
* `image` and `features` are optional and often absent right now — fall back gracefully (gradient/initial-based placeholder art when no `image`; just show `description` when no `features` list).

**Certificate object shape:**
```json
{ "issuer": "HackerRank", "folder": "https://github.com/ashrma0502/Certificates/tree/main/HackerRank" }
```

**Required states:** a loading skeleton while the fetch is in flight, and a graceful fallback (friendly inline message, not a crash) if the fetch or JSON parsing fails. Session-level caching (e.g. `sessionStorage`) is a nice-to-have so repeat visits within a session skip the re-fetch.

## Extensibility — Config-Driven Content

Projects and Certificates already solve the "easy to update" problem by living outside the codebase entirely. Everything else that's a *list the person will grow over time* — rotating roles, expertise tags, skills (including whole new skill categories), and project types — needs the same philosophy applied one level down: one plain-data config file, never hardcoded inline in JSX. Components render generically off however many items exist; adding one should never mean touching component logic.

**`src/lib/constants.js`** (single source of truth for this content):
```js
export const ROLES = [
  "Frontend Developer",
  "Data Engineering",
  "AI/ML Enthusiast",
  "Full-Stack Developer",
];

export const EXPERTISE = ["C", "Java", "Python", "Frontend Engineering", "DBMS", "Data Engineering"];

export const SKILLS = [
  { category: "Programming Languages", items: ["C", "Java", "Python", "JavaScript", "SQL"] },
  { category: "Frameworks/Libraries", items: ["React", "Flask", "FastAPI", "Streamlit", "Tailwind CSS", "Bootstrap"] },
  { category: "Databases", items: ["MySQL", "DuckDB"] },
];

export const PROJECT_TYPES = {
  personal:  { label: "Personal",  order: 1 },
  college:   { label: "College",   order: 2 },
  hackathon: { label: "Hackathon", order: 3 },
};
```

**Rules that make this actually future-proof, not just relocated:**
* The typing-effect component loops over `ROLES.length`, not four hardcoded strings — a fifth role is a one-line array push, no JSX touched.
* The expertise grid and each skill-category's item list use CSS grid with `auto-fill`/`auto-fit` (or equivalent flex-wrap), never a fixed column count tied to today's item count — 4 cards and 10 cards should both look intentional.
* The Skills section iterates over `SKILLS` to render category groups — a new category (e.g. "Cloud/DevOps" later) is one object appended to the array, not a new hardcoded block in JSX.
* Project filter tabs are built from `PROJECT_TYPES`, not four hardcoded `<button>`s. If a project's `type` value from the live README isn't in `PROJECT_TYPES` yet, fall back to a title-cased version of the raw string rather than hiding the project or crashing — a new type in the README should never silently break filtering just because the config hasn't caught up yet.

*(Optional, not required for v1: since Projects and Certificates already live-fetch from the README with zero redeploys, the same hidden-JSON-comment pattern could later extend to `ROLES`/`EXPERTISE`/`SKILLS` too — e.g. a `SITE_CONFIG_JSON` block — if the goal ever becomes "never touch the codebase for any content change." `constants.js` is the simpler starting point, and this content tends to change far less often than the project list does.)*

## Tech Stack

* **Framework:** React + Vite (SPA — not Next.js)
* **Styling:** Tailwind CSS
* **Animation:** Framer Motion, GSAP (with ScrollTrigger), Lenis for smooth scroll
* **3D:** Three.js via React Three Fiber + Drei
* **Deployment:** Vercel (Vite framework preset)

## Design System

* **Theme:** Futuristic — glassmorphism, neumorphism accents, dynamic gradients, interactive 3D elements, micro-interactions, parallax, immersive storytelling over static bio-page conventions.
* **Inspiration:** Apple, Stripe, Linear, Vercel, Framer, Arc Browser, Awwwards-tier sites.
* **Color palette:**
  - Background: `#050816`, `#0B1026`, `#121826`
  - Primary: `#8B5CF6`, `#06B6D4`, `#22D3EE`
  - Accent: `#EC4899`, `#A855F7`, `#22C55E`

## Global UX Requirements

* Custom cursor (replaces the OS cursor; scales/morphs on hover over interactive elements)
* Magnetic buttons (subtle pull toward cursor proximity)
* Lenis-powered smooth scrolling site-wide
* Page/section transition animations
* Scroll-triggered reveals (GSAP ScrollTrigger or Framer Motion `whileInView`)
* Short loading-screen animation on first paint
* Ambient background motion (particles/gradients) that doesn't compete with foreground content
* All of the above must degrade gracefully — respect `prefers-reduced-motion`, and drop to lighter/static equivalents on low-end devices rather than forcing full 3D everywhere

## Three.js Requirements by Section
* **Hero:** interactive orb, particle universe, floating geometric shapes
* **Skills:** rotating skill globe with interactive nodes
* **Projects:** a 3D presentation layer for the featured/expanded project view
* **Background (global):** animated stars, floating gradients, ambient particles
* **Target:** 60fps — profile with the R3F `<Perf>` helper during dev; lazy-load heavy 3D scenes (`React.lazy` + `Suspense`) and drop to a static/CSS-only fallback below a sensible viewport-width or `prefers-reduced-motion` threshold

## Animation Requirements
* Framer Motion + GSAP for: fade-in, slide-reveal, scale, parallax scroll, staggered text reveals, morphing transitions

## Responsive Design
* Mobile, tablet, laptop, desktop, ultrawide
* Touch-friendly interaction targets, layouts that genuinely re-flow (not just scale down), animation complexity reduced on mobile viewports

## Performance & SEO
* **Target:** Lighthouse 90+, lazy loading, code splitting, dynamic imports, optimized images
* **SEO caveat, since this is a client-rendered SPA (not Next.js):** true per-route SSR metadata isn't available. For a single-page portfolio this is a minor loss — set strong static `<meta>`, Open Graph, and Twitter Card tags directly in `index.html`, add a hand-written `sitemap.xml` and `robots.txt` to `public/`, and inject `Person` JSON-LD structured data once at load. If search visibility becomes a priority later, prerendering (`vite-plugin-prerender`) or a move to Next.js/Astro are the natural upgrades — not needed for v1.
